# 유튜브 자동 이미지 생성기

다큐 영상용 이미지·영상 프롬프트를 **스펙 한 장에서 전부 찍어내는** 도구.
현재 프로젝트: 거북선 — 불을 뿜는 무적함선의 진실 (`spec/isunsin.json`).

**14블록 · 51비트 · 이미지 183장 · 영상 132개**

## 구조

```
블록(Block) 1~14        영상의 서사 단락. 블록마다 내용·조명이 다르다
 └ 비트(Beat) B1~B5     블록 안의 장소 단위
    └ 컷(Cut) K1~K5     같은 장면을 카메라만 좁혀가며 뽑은 연속 컷
       └ 클립 V1~V4     컷과 컷 사이를 잇는 영상 (비트당 컷수-1개)
```

파일명은 `1블-b1-k1.png`, 그 사이 영상은 `1블-b1-v1.mp4`.
이 규칙을 지켜야 편집 타임라인에서 순서대로 정렬된다.

## 설치

필요 없다. 파이썬 3.10+ 표준 라이브러리만 쓴다.

## 쓰는 법

```bash
# 1. 작업 시트·매니페스트·대기열 생성
python3 -m src.cli build

# 2. 규모 확인
python3 -m src.cli stats

# 3. 저장 폴더 대조 (어디까지 했나)
python3 -m src.cli verify --kind image

# 4. 이어서 만들 프롬프트 (중단 후 재개)
python3 -m src.cli next -n 5

# 5. 특정 한 장만
python3 -m src.cli show 2블-b1-k4
```

`build` 결과물은 `out/`에 떨어진다.

| 파일 | 용도 |
| --- | --- |
| `프롬프트시트_나노바나나.md` | **실제로 쓰는 것.** 자연어 프롬프트, 파일명과 짝지어 순서대로 |
| `프롬프트시트_미드저니.md` | 원본 스펙 문법 그대로 (`--ar --sref --sw --no`) |
| `매니페스트.csv` | 315행 전체 목록. 엑셀로 열어 진행 상황 체크 |
| `대기열_이미지.tsv` | `파일명<TAB>프롬프트`. 붙여넣기 자동화용 |

## 두 가지 프롬프트 모드

원본 스펙은 **미드저니 문법**(`--ar 16:9 --sref [SEED] --sw 110 --no ...`)으로 쓰여 있다.
그런데 **나노바나나 프로와 Google Flow는 이 플래그를 이해하지 못한다** — 그냥 무시하거나
글자로 읽어버린다. 그래서 같은 스펙에서 두 벌을 낸다.

- `mj` — 원본과 글자 단위로 동일. `[CAST]` 등 자리표시자를 그대로 둔다
- `natural` — 자리표시자를 실제 문장으로 펼치고, 플래그를 평범한 영어로 바꾼다

`next`와 `show`는 기본이 `natural`이다. `--mode mj`로 바꿀 수 있다.

## 그림체를 하나로 묶는 법

183장이 한 사람이 그린 것처럼 보여야 한다.

1. `1블-b1-k1`을 먼저 한 장 뽑는다.
2. 마음에 드는 결과의 **시드 값**을 확보한다.
3. 이후 모든 프롬프트의 `[SEED]` 자리에 그 값을 넣는다.

`[CAST]` `[LOCK]` `[R-PAINT]` `[STYLE]` `[FORBIDDEN]` 다섯 덩어리는 183장 내내 고정이다.
`natural` 모드는 이걸 이미 프롬프트 안에 펼쳐 넣어준다.

## 작업 순서

이미지와 영상은 도구가 다르므로 **단계를 나눈다.**

1. **이미지 183장** — 나노바나나 프로에서 16:9, 1장씩. `--kind image`
2. **영상 132개** — Flow Omni에서 K1→K2 식으로 두 장씩 넣어 잇는다. `--kind video`

중간에 크레딧이 떨어지거나 세션이 끊기면 `verify`로 상태를 보고 `next`로 이어간다.
폴더에 실제로 있는 파일을 기준으로 판단하므로 별도 진행 기록이 필요 없다.

## 블록을 추가·수정할 때

`spec/isunsin.json`의 `blocks` 배열에 한 줄 넣고 `build`를 다시 돌린다.

```json
{ "no": 15, "title": "...", "light": "B", "seconds": 70, "tempo": "중간",
  "anchors": 12, "clips": 9, "beats": [["B1",4],["B2",4],["B3",4]] }
```

- `light` — A/B/C/D (뜻은 `lights`에)
- `beats` — `["장소코드", 컷수]` 목록
- `anchors` / `clips` — 원문 헤더의 값. **검증용이다**

## 검증이 막아주는 것

로드할 때마다 이 항등식을 확인하고, 어긋나면 즉시 실패한다.

```
앵커 합 − 비트 개수 == 클립 합
```

비트 하나는 컷 N개와 그 사이 영상 N−1개를 만들기 때문이다. 1~13블록 전부 성립한다.

이 항등식 덕분에 **원문이 잘린 14블록도 추측 없이 복원**했다 —
헤더가 `앵커 12 · 클립 9`이므로 비트는 3개, 컷은 4/4/4다.

컷수를 잘못 적으면 수백 장을 만든 뒤에야 알아차리게 된다. 그래서 로드 시점에 막는다.

## 테스트

```bash
python3 -m unittest discover -s tests
```

`mj` 모드가 원본 스펙과 글자 단위로 같은지까지 검사한다.

## Flow 자동화는 왜 코드에 없나

Google Flow에는 공개 API가 없다. 브라우저를 스크립트로 조종하는 방법은
로그인 세션·화면 구조 변경에 그대로 깨지고, 이 저장소가 다룰 범위를 넘어선다.

그래서 **결정론적으로 자동화할 수 있는 부분**(프롬프트 생성, 파일명 규칙,
진행 상황 추적, 재개 지점 계산)만 코드로 만들었다. 생성 버튼을 누르는 일은
Claude in Chrome 같은 브라우저 도구나 손으로 한다 — `대기열_이미지.tsv`가
그쪽에 그대로 먹이기 좋은 형식이다.

## 스킬

`.claude/skills/geobukseon-images/SKILL.md` — 이 저장소를 Claude에서 열면 자동으로 붙는다.
브라우저 세션에서 실제로 생성을 돌릴 때 쓰라고 만든 것으로, 지난번에 겪은 두 가지
구조적 실수를 규칙으로 박아 넣었다.

- K1은 **새 생성**, K2부터는 **같은 스레드에서 편집**. 비트가 바뀌면 다시 새 생성
- 블록마다 내용이 다르므로 프롬프트는 `next`/`show`에서 받아 **그대로** 쓴다

한도에 걸렸을 때의 처리(재시도 반복 금지, 멈춘 지점 보고, 결제·로그인 대행 금지)도 함께 적었다.
